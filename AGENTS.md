# AGENTS
- Operon AI is a read-only JWT/oe_is_curador-gated edge service with independently validated, source-backed field suggestions; the curation form stages them until explicit review, and rounds use a separate confirmed RLS-backed upsert preserving existing records. PDF text extraction uses bounded, sequential page batches via authenticated self-invocations of the same function so each batch has an independent CPU budget; every batch revalidates admission and official agency HTTPS PDF DNS/redirect/size allowlists, and complete text is required before AI generation. OpenRouter calls disable reasoning and use structured JSON with short contiguous evidence separate from complete field values; fallback diagnostics log only model and sanitized status, preserving rate-limit and timeout errors without exposing payloads.
- Operon detail derives a dated timeline client-side from released events, rounds, documents and the edital publication date, deduplicating by instant and label; module types reuse generated migration fields to avoid schema drift.
- Operon curation fetches status-independent lists and derives combined-filter tab counts from the same cache; optimistic status transitions snapshot and restore that cache so publication keeps selection visible without changing the public portal.
- Operon portal is a nested /editais layout (sidebar + Outlet) whose pages share one per-user React Query cache via usePortalOperon; indicators, sorting, filters and CSV are pure client functions in operon-indicadores/operon-chamadas, and cross-user aggregates require a curator-only aggregate RPC, never client reads of other users' rows.
- Operon user portal uses a published-only query layer with explicit released-event filtering and user-scoped following; this prevents exposure of pending events and keeps notification delivery outside the frontend.
- Operon geographic scope uses AbrangenciaBadge and shared scope options/matching for both views; this keeps curator and published filters consistent without schema changes.
- Operon source identity uses one slug-to-Badge-variant map in operon-fontes and FonteBadge with global color tokens; portal options use active organization configs visible through session RLS, while curation uses all active sources only after oe_is_curador confirms access. Separate query cache keys prevent curation options leaking into the portal; shared sphere matching keeps edital scope separate.
- Operon Fomento uses the shared Supabase session with a dedicated module login and reads existing role and organization-config RLS results for admission; this keeps module entry points separate without parallel authentication or tenant models.
- Operon protected entry uses an RLS-backed admission gate and navigates to its login before sign-out; recovery return paths are allowlisted and carried by the existing email sender, preventing cross-module redirects without new authentication infrastructure.
- Service Desk operations: one Central de Atendimento at /servicedesk/atendimento for every responsible group (context via ?grupo=); stage type (analysis = 1st step, execution = later steps) and modules derive from service steps, never group names; legacy /servicedesk/<group code> redirects there; VPN release goes through `sd_release_vpn` + private `servicedesk` bucket path `<org>/vpn/<request>/` and `sd-notify` event `liberar_vpn`.

- Service Desk tenant = `public.organizations`; every `sd_*` table carries `organization_id` and RLS uses `sd_is_member`/`sd_is_admin`/`sd_in_group` — keeps institutions isolated without a parallel tenant model.
- Institution-specific rules (durations, contract types, alert lead times, groups) live in `sd_settings`/`sd_groups`, never in code — the module must serve multiple institutions.
- The `institutions` table is the eMEC catalogue for profile affiliation, not a tenant — do not reuse it for Service Desk.
- Student account status is module-scoped through `sd_students.service_desk_access_active`; never disable the shared ProjetoGO account when blocking Service Desk access.
- Service Desk areas: /servicedesk routes each user to Portal (sd_students/sd_faculty), a panel per responsible group (/servicedesk/<group code>, approver vs executor derived from service steps, never from group names) or /servicedesk/admin; request detail at /servicedesk/solicitacao/:id — one shared request/notification model, no parallel user structures.
- Public institution guides are orientation-only entry pages that reuse existing Service Desk login and first-access routes, never parallel authentication or workflows.
- Operon Telegram linking: the portal only generates single-use codes and reads status through SECURITY DEFINER RPCs; only the external Hermes bot (service role, getUpdates) confirms links via `oe_confirmar_vinculo_telegram`, so the portal never creates webhooks or stores the bot token. Bot username comes from `VITE_OPERON_TELEGRAM_BOT` because the bot may be replaced.
- Telegram expiry feedback remembers only the last observed expiry for the current user in component state and uses a cleaned-up local clock; this preserves expired-code feedback after the status RPC clears pending codes without persisting tokens or changing RPCs. Telegram and following write controls use the central view-as state in addition to the global fetch guard.
- "Ver como" role simulation is one central override (`src/lib/view-as.ts`) applied inside AuthContext/FomentoAuthContext and role gates; it is accepted only when the real `profiles.fomento_role` read from the database is superadmin, lives only in sessionStorage, and a fetch guard installed before the Supabase client blocks every write while active, because the database still authorizes as superadmin.
- Tenant boundaries: ordinary admins (Admin Org and equivalents) operate only within their own organization; only the real superadmin crosses organizations and sees the role and organization selectors.
- The global ViewAsBar uses an explicit protected-panel route allowlist and authenticated, loaded real-role checks; public entry pages must never render its controls or simulation banner.
- Operon headers share OperonUserMenu with user-keyed name caching and effective-role navigation; its profile writer authenticates the current user and sends only full_name, with simulation checked before and after session lookup, so identity editing cannot change roles or another user's profile.
- Operon publication date prefers the agency `publicado_em`; `verificado_em` is only a fallback marked "data aproximada" (tooltip + CSV suffix) via `dataPublicacaoInfo` in operon-chamadas, the single source for filters, sorting, indicators and CSV.
- Operon collection health derives per source from `oe_coleta` in operon-coletas (Ok <36h since last success and no consecutive failures; Atenção >36h or 1-2; Falha 3+; Sem coleta when none) — pure client rules, no new queries.
- Operon user indicators call the aggregate RPC `oe_indicadores_usuarios` (curator-only, allowlisted as read-only in the view-as guard); when the function does not exist yet, the UI shows an activation notice instead of an error.
- Operon edital values derive in operon-valores: only total/estimado with valor_confirmado_em enter sums; por_agencia, unconfirmed and empty values are always listed separately, never estimated.
